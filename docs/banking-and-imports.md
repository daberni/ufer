# Banking and imports

This guide describes the current bank integration, financial data behavior and supported import formats. For installation and deployment, see [setup and operation](setup.md). For planned capabilities, see the [feature comparison](feature-comparison.md).

## Bank synchronization

The current provider is [Enable Banking](https://enablebanking.com/docs/api/reference/). Ufer uses account information endpoints only: application JWTs, institution discovery, authorization, sessions, balances, and paginated transactions. It does not initiate payments.

Sandbox and production data are isolated. Sandbox institutions do not establish production bank coverage. Live access requires a production application and the provider's account-linking or commercial onboarding process. [Restricted own-account access](https://enablebanking.com/docs/api/linked-accounts/) is intended for evaluation and individual non-commercial use; it is not a contract for a hosted SaaS product.

Authorizations expire according to the institution's consent duration. The UI warns seven days before expiry and supports reconnecting. An expired connection keeps its row, accounts and reconnect prompt; if the provider reports its session as ended during a sync, the stored session ID is deleted. Passing the local consent expiry does not start a provider revocation: the expired row retains its encrypted session ID until explicit removal or a confirmed terminal provider response. Stable identification hashes match reconnects to existing accounts; a changed account currency prevents automatic remapping. A reconnect that takes over all accounts of an earlier connection marks it superseded. Its initiating callback makes one attempt to revoke each newly superseded session, and also one attempt for its new session if account mapping fails. A failed attempt does not undo the new linked connection: the released connection remains visible with its credential and an error asking the user to remove it. Unrelated callbacks and scheduled syncs never retry that revocation. A callback that returns with an error, for example after the user cancelled at the bank, consumes its pending state, so the callback URL cannot be used afterwards.

Bank connections can be removed from the Bank connections view after a confirmation that lists the effects. Ufer first asks Enable Banking to delete the session (`DELETE /sessions/{session_id}`), which closes the bank consent where the bank supports it. Only a confirmed revocation or a known terminal response (`EXPIRED_SESSION`, `CLOSED_SESSION`, `REVOKED_SESSION` or `SESSION_DOES_NOT_EXIST`) completes removal: the credential is deleted and the accounts detached in the same transaction. The linked accounts keep their balances, balance snapshots, transactions and categories; syncs then skip them and balances stay at the last synced value. If the provider call fails, the API returns a safe 502 Problem Details error. The dialog remains open and the connection, account links and credential remain unchanged so the user can retry removal. There are no background revocation retries. Removal holds the sync lease through the provider call and local update and is refused while a sync runs or a callback is still exchanging its authorization code. The final transaction removes only the exact session inspected before revocation. If a callback links a new session meanwhile, removal returns 409 without detaching accounts or deleting the new credential; retrying removal then revokes that session. The removed connection no longer appears in the list. Connecting the same bank again later maps the kept accounts through identification hashes instead of creating duplicates. The dialog can also archive the kept accounts whose balance is 0 in the same transaction; accounts with another balance stay active, the dialog names them beforehand and a message lists them afterwards. Archived accounts leave the account lists, the overview and pickers, keep counting in reports and can be restored from the account details. Bank sync skips archived accounts, also while their connection stays linked; the connection's other accounts keep syncing, and a restored account catches up within the provider's transaction window on the next sync. A detached account can be converted to a manual account from its details: it keeps its history and its last bank balance, and later connections to the same bank create a new account instead of syncing into it. A detached account can also be deleted permanently with its bookings and balance history after typing its name; linked bookings on other accounts stay as transfers without a counterpart. Both actions are refused while a sync runs.

Sync retrieves a rolling 89-day window, processes accounts sequentially, follows all continuation pages, and persists only booked (`BOOK`) transactions. Deduplication uses `entry_reference` per account; `transaction_id` is not reliably unique. Missing or conflicting references stop that account's import. Manual category corrections, including deliberately uncategorized transactions, survive repeat imports. Provider references and account links exist today. Each sync run in the history links to the transactions it inserted (see [architecture](architecture.md)); runs recorded before this link show their count without a list. CSV import batches, a complete provenance trail and editable transaction overrides are planned.

Every Enable Banking response is validated against the fields Ufer reads, persists or shows before it is used. A response that does not match, such as a missing session expiry, an unparseable balance date or a booking without an amount, is a 502 provider failure and nothing from it is stored. Malformed optional descriptive values such as counterparty names, account names or remittance lines are dropped instead of stopping an import. Session expiries are stored in the persisted UTC timestamp format.

Application keys stay on the server. Bank session IDs are encrypted with AES-256-GCM. Authorization callbacks bind the initiating user, exact live authentication session, active installation-workspace membership and browser secret, expire after 15 minutes, and are single-use. Back up the database and encryption key together. Financial database contents are not end-to-end encrypted.

## Data and imports

Amounts use integer minor units. Different currencies are never silently converted or summed. The dashboard separates latest known asset balances from month-filtered cash flow. Every transaction has a type (income, expense, transfer; opening balance and adjustment for manual accounts) independent of its category, and only income and expenses count toward cash flow, spending and trends. A synced booking whose counterparty IBAN belongs to another synced account becomes a transfer; otherwise new bookings start as income or expense by direction. Rules assign categories to transfers like to any other booking, and a transfer no rule matches stays uncategorized. After each sync and CSV import, a transfer and an unlinked booking with the opposite amount in the same currency on another own account at most three days apart are linked as one transfer when each has exactly one such candidate. Manual type changes, links and unlinks survive resync and imports. A person links only bookings with the exact opposite amount in the same currency at most 14 days apart; transfers with a fee or a currency exchange stay transfers without a counterpart. A transfer someone saved without a counterpart is never paired automatically afterwards. See [ADR 008](adr/decisions/008-transaction-types-and-transfers.md).

The schema includes accounts, transactions, categories, categorization rules, bank connections (`requisitions`), account identifiers, balance snapshots, sync history, leases, and login throttling. Drizzle provides typed table models, a shared database connection and versioned SQL changesets. Empty databases receive the initial schema; a recognized existing database opens without automatic schema/history changes. Existing-database adoption and future upgrades require explicit maintenance; see the [migration workflow](database-migrations.md). Individual users and active membership of one constrained installation workspace are implemented in source; independent-customer isolation and SSO remain unimplemented. See [user management](user-management.md) for the required rollout.

Manual accounts accept transactions entered in Ufer, Update balance and CSV imports. A manual account's balance is the sum of its transactions: the opening balance booked when the account is created, entered or imported transactions, transfers and adjustments ([ADR 009](adr/decisions/009-manual-account-balances-from-transactions.md)). The transaction-history import ([#14](https://github.com/daberni/ufer/issues/14), stages 1 and 1b) starts with Import CSV in the transactions view: a small dialog takes the file by drop or file chooser, closing it stays on the transactions view, and choosing a file opens the page at `/transactions/import` with that file already loaded. The file is handed over in memory only; opened directly or reloaded, the page shows its own drop zone, and Cancel import returns to the transactions view. It reads any CSV in the browser: encoding (UTF-8 with or without BOM, otherwise Windows-1252), delimiter, decimal separator and date format are detected and shown as compact, adjustable controls. Each column of the preview table has a role select in its header (date, payee, description, amount, debit, credit, currency, category, account, ID or ignore), suggested from the header names. Without an account column, all rows go to one target account; with one, each distinct account value with its row count goes to an existing manual or bank-linked account (an account with the same name is preselected), a new manual account named after the value, or is skipped. A check reports new rows, rows already in Ufer, possible duplicates, rows needing review and row errors before anything is saved; a review filter shows only the rows needing attention with their reason, and a single primary action then imports the new rows. Missing or invalid inputs (an account without a target, an incomplete new account, unassigned required column roles) are marked next to the input itself; the primary action stays enabled, and pressing it scrolls to and focuses the first one instead of sending anything. Mapped rows are sent in batches of at most 2,000 rows and about 1 MB, so files up to 25 MB stay below hosted request limits. While a check runs or after a confirmation started, the page asks once before it is closed, reloaded, left through a link or left with the browser's Back or Forward button; a guard history entry is held only while the import is unfinished.

A new manual account asks for a balance, by default today's: the difference between that balance and the sum of its imported rows is booked as an opening balance on the file's first date for that account. Alternatively the balance at the start of the file is booked as given on that date. Every confirmed batch recalculates the opening balance, so after the last batch the account's balance equals today's balance; without a balance the account starts at zero.

Duplicates are rows the target account already holds. A row matches an earlier mapped import by its `csv:m:` reference: with an ID column, the reference derives from the export's ID, so a reimport recognizes a row even when its text changed; an empty ID, an ID longer than 200 characters or one that appears more than once for the same target account is a row error. Without an ID column the reference derives from the content (date, amount in minor units, normalized payee and description, and the occurrence of equal rows in the file); rows saved by a mapped import match only this way, so batches of one file never mistake each other for duplicates. Any other booking matches when it has exactly the same amount and matching text (one normalized text contains the other, or they share a word of four or more Unicode letters or digits; text without letters or digits never matches). A booking on the same date wins; otherwise the only booking at most three days apart matches. When several bookings in that window could match, the row is listed as a possible duplicate and imported, not skipped. Each existing booking absorbs at most one row across all batches. Checking and confirming classify a batch with the same function; confirming does so inside its write transaction, so the check reports what confirming saves and a concurrent bank sync cannot cause duplicates. Amounts are parsed exactly (at most 15 integer and 6 fraction digits, one sign marker, consistent thousands separators) and may carry one currency symbol or ISO 4217 code, which must agree with the other amount column, the currency column and the account; anything else is a row error. Two-digit years map to the most recent century that is not in the future. Row numbers are physical lines in the file, including blank lines and line breaks inside quoted fields. Occurrences of identical rows are counted per target account, so references do not depend on row order or on which other accounts an export contains. New manual accounts are created with the first confirmed batch under an ID derived from the import and source account, so retries never create a second account; once created, its name and currency are fixed for that import.

A later bank sync applies the same rule to rows a mapped import saved on that account: a matching row adopts the bank reference and provider data and keeps its category instead of a duplicate being inserted; ambiguous matches insert the bank booking. Confirmation inserts new rows only, so confirming again saves nothing and never changes existing categories. The categories section lists each distinct category value with its row count. A value whose name matches an existing category (ignoring case and canonically equivalent spellings) uses it; any other value creates that category on confirmation; either can be changed to another existing category or to the rules. A value holding several comma-separated tags, as Buxfer exports them, is not guessed: it counts as needing review and its rows are categorized by rules unless a category is chosen for it. Tags that carry amounts, as Buxfer exports a split transaction (`Car / Fuel:45.52,Groceries:5.88`), split the row instead: each tag becomes a part with its amount, signed like the row (a negative tag amount counts against it), and each tag name is listed in the categories section like any other value. A split booking is saved with its parts, so rules neither categorize nor retype it, and importing the file again adds neither bookings nor parts. Tags that carry amounts but do not form a valid split (a tag without an amount among tags with amounts, a single tag with an amount, a part of 0, amounts that do not add up exactly to the row's amount, more decimals than the account currency has, or a transfer) are not intercepted: the row imports as an ordinary unsplit booking that rules categorize like any other, and the original tags are appended to its description (`… · Split: Car / Fuel 45.52, Groceries 5.88`), so nothing from the export is lost. Only a file mapped with the Buxfer template (the built-in one or a saved template for its header) reads tags this way; in any other file, a category such as `Project:2026` stays a plain category value. Rows without a category are categorized by rules. Rows imported into a bank-linked account appear in its history but do not change its bank-reported balance. A file whose header row equals a template's, cell by cell after trimming, is mapped with that template automatically, and the page says so ("Detected as Buxfer export" or "Using your template …"); Map manually switches back to the detected number and date format and suggested roles while keeping the current encoding and delimiter, and a match that is not applied is offered with Apply template. The built-in Buxfer template recognizes `ID,Date,Description,Currency,Amount,Type,Tags,Account,Status,Memo,IOU` and maps ID, ISO date, description, currency, signed dot-decimal amount, Type, Tags as category and Account as source account; Status, Memo and IOU are ignored. Any file can map a Type column by choosing that role; it is never suggested from a header name, because a bank export's "Transfer" can mean an external payment. Rows whose type is "Transfer" (or "Umbuchung"/"Übertrag") are saved as automatic transfers, which the transfer pairing links to their counterpart after confirmation; every other row is income or expense by its sign. Descriptions Buxfer shortened with "..." still match the full bank text during duplicate detection, because a shortened text is contained in the full one. After a confirmed import the mapping can be saved as a named template, or, when a saved template matches the header (also after Map manually), that template is updated: column positions in the exact header row (so repeated header names keep their roles), the date and decimal format, and optionally the chosen existing accounts by source value and existing categories by category value. Saved templates are stored server-side in `import_templates` (changeset 0013) and are unique per header row and per name (ignoring case). The import page lists saved and built-in templates together, saved ones first, which is also the matching order, so a saved template for the Buxfer header wins. Built-in templates stay defined in code: they are listed as "Buxfer export (built-in)", cannot be renamed or deleted, and Duplicate saves an editable copy. Saved templates can be renamed and deleted. Remembered accounts or categories that no longer exist fall back to the defaults. Reimporting never updates rows that are already imported. There is no PDF importer or dedicated migration wizard for another product.

Balance snapshots record a synced account's provider balance on a given date. A manual account records a balance instead as an adjustment: Update balance and each imported balance book the difference between the entered balance and the account's balance at the end of that date, so a market value that cannot be reconstructed from cash transactions alone is kept in the account's running balance. Historical net-worth charts are planned; no history chart is available yet.

Manual accounts import a balance series from their details page (Import balances):

```csv
date;balance;currency
2026-01-15;1000.00;EUR
```

Rows are recorded oldest first. Each books an adjustment for the difference to the account's balance at the end of its date (an opening balance if the account has no transactions yet); a balance the account already has books nothing, so importing the same file again changes nothing. Later transactions keep their effect, so an older balance does not replace the current one.

Rules match payee and description case-insensitively. Rules match in the order of the rule list, which is stored as internal priorities; equal priorities retain the persisted rule-ID tie-break. New rules, including those created from an assignment, are added at the end of the list. Applying rules preserves manual assignments. A manually assigned category's dashed lightning action explicitly opens a matching-rule form. Solid lightning identifies a rule-assigned category. Syncs, imports, manual entries and rule application record the deciding rule, and its solid lightning opens that rule's editor. Assignments made before Ufer recorded the rule, or by a rule deleted since, keep a noninteractive indicator; the application does not guess historical attribution, and applying rules again records the current deciding rule. Uncategorized has no indicator. Saving a category never opens a prompt automatically. The form proposes a keyword from the payee or description and waits for a settled preview of the current pattern. Creation stores the same UUID used by that preview. The transaction the rule was created from becomes rule-assigned, referencing the new rule, when that rule decides its category in the current matching order (same category, matching pattern, no earlier rule deciding it); otherwise it stays manual. Optional application affects only transactions that are still uncategorized; other manual assignments stay manual. Both happen in the rule's creation transaction. Regular expressions use RE2 syntax without backreferences or lookbehind.


### Recorded bank balance classification

A bank balance observation retains the selected provider `balance_type` alongside its amount and date. The history source label distinguishes closing booked, interim booked, closing available, interim available, previous closing booked and expected balances; observations recorded before this provenance was retained show only “Bank sync”, without inventing a classification. These are provider classifications, not a claim that Ufer certifies historical bank closing balances. Daily values reconstructed from transactions are labelled as estimates and do not inherit the anchor's bank classification. Selection priority is unchanged. Code meanings follow the [Enable Banking API reference](https://enablebanking.com/docs/api/reference/).


### Account display names

Open an account's details and select its heading to rename it, for both manual and bank-linked accounts. Names are trimmed and must contain 1–100 characters. Duplicate display names are allowed: immutable account IDs and provider identifiers distinguish accounts. Renaming changes no bank identity, connection, balance or transaction. Account lists and transaction labels refresh after saving.

A bank-supplied account name or product remains visible in the details as “Bank account name” when known. A reconnect may refresh that provider label but preserves the custom display name. Existing installations have no recoverable separate provider label until the bank supplies it during a later authorization; no historical name is inferred.
