# CSV import

This guide describes importing transaction history from CSV files. Bank synchronization and data handling are described in [banking](banking.md).

## Mapping

The transaction-history import ([#14](https://github.com/daberni/ufer/issues/14), stages 1 and 1b) starts with Import CSV in the transactions view: a small dialog takes the file by drop or file chooser, closing it stays on the transactions view, and choosing a file opens the page at `/transactions/import` with that file already loaded. The file is handed over in memory only; opened directly or reloaded, the page shows its own drop zone, and Cancel import returns to the transactions view. It reads any CSV in the browser: encoding (UTF-8 with or without BOM, otherwise Windows-1252), delimiter, decimal separator and date format are detected and shown as compact, adjustable controls. Each column of the preview table has a role select in its header (date, payee, description, amount, debit, credit, currency, category, account, ID or ignore), suggested from the header names. Without an account column, all rows go to one target account; with one, each distinct account value with its row count goes to an existing manual or bank-linked account (an account with the same name is preselected), a new manual account named after the value, or is skipped. A check reports new rows, rows already in Ufer, possible duplicates, rows needing review and row errors before anything is saved; a review filter shows only the rows needing attention with their reason, and a single primary action then imports the new rows. Missing or invalid inputs (an account without a target, an incomplete new account, unassigned required column roles) are marked next to the input itself; the primary action stays enabled, and pressing it scrolls to and focuses the first one instead of sending anything. Mapped rows are sent in batches of at most 2,000 rows and about 1 MB, so files up to 25 MB stay below hosted request limits. While a check runs or after a confirmation started, the page asks once before it is closed, reloaded, left through a link or left with the browser's Back or Forward button; a guard history entry is held only while the import is unfinished.

A new manual account asks for a balance, by default today's: the difference between that balance and the sum of its imported rows is booked as an opening balance on the file's first date for that account. Alternatively the balance at the start of the file is booked as given on that date. Every confirmed batch recalculates the opening balance, so after the last batch the account's balance equals today's balance; without a balance the account starts at zero.

## Duplicates

Duplicates are rows the target account already holds. A row matches an earlier mapped import by its `csv:m:` reference: with an ID column, the reference derives from the export's ID, so a reimport recognizes a row even when its text changed; an empty ID, an ID longer than 200 characters or one that appears more than once for the same target account is a row error. Without an ID column the reference derives from the content (date, amount in minor units, normalized payee and description, and the occurrence of equal rows in the file). Otherwise a booking matches by content, whichever source saved it, including an earlier mapped import of another export (for example a card issuer's statement after a Buxfer export): exactly the same amount and matching text (one normalized text contains the other, or they share a word of four or more Unicode letters or digits; text without letters or digits never matches). A booking on the same date wins; otherwise the only booking at most three days apart matches. A synced bank booking matches on its value date or its bank booking date, since exports record either. Rows that earlier batches of the same import saved never match by content, so batches of one file never mistake each other for duplicates. A row is listed as a possible duplicate and imported, not skipped, when several bookings in that window could match, when a booking of the same amount on the same date has a different text, or when a transfer of the same amount lies in the window, since a card statement's settlement ("Einzug aus letzter Abrechnung") and the bank side's transfer name the same movement differently. Each existing booking absorbs at most one row across all batches. Checking and confirming classify a batch with the same function; confirming does so inside its write transaction, so the check reports what confirming saves and a concurrent bank sync cannot cause duplicates. Amounts are parsed exactly (at most 15 integer and 6 fraction digits, one sign marker, consistent thousands separators) and may carry one currency symbol or ISO 4217 code, which must agree with the other amount column, the currency column and the account; anything else is a row error. Two-digit years map to the most recent century that is not in the future. Row numbers are physical lines in the file, including blank lines and line breaks inside quoted fields. Occurrences of identical rows are counted per target account, so references do not depend on row order or on which other accounts an export contains. New manual accounts are created with the first confirmed batch under an ID derived from the import and source account, so retries never create a second account; once created, its name and currency are fixed for that import.

A later bank sync applies the same rule to rows a mapped import saved on that account: a matching row adopts the bank reference and provider data and keeps its category instead of a duplicate being inserted; ambiguous matches insert the bank booking. Confirmation inserts new rows only, so confirming again saves nothing and never changes existing categories.

## Categories and splits

The categories section lists each distinct category value with its row count. A value whose name matches an existing category (ignoring case and canonically equivalent spellings) uses it; any other value creates that category on confirmation; either can be changed to another existing category or to the rules. A value holding several comma-separated tags, as Buxfer exports them, is not guessed: it counts as needing review and its rows are categorized by rules unless a category is chosen for it. Tags that carry amounts, as Buxfer exports a split transaction (`Car / Fuel:45.52,Groceries:5.88`), split the row instead: each tag becomes a part with its amount, signed like the row (a negative tag amount counts against it), and each tag name is listed in the categories section like any other value. A split booking is saved with its parts, so rules neither categorize nor retype it, and importing the file again adds neither bookings nor parts. Tags that carry amounts but do not form a valid split (a tag without an amount among tags with amounts, a single tag with an amount, a part of 0, amounts that do not add up exactly to the row's amount, more decimals than the account currency has, or a transfer) are not intercepted: the row imports as an ordinary unsplit booking that rules categorize like any other, and the original tags are appended to its description (`… · Split: Car / Fuel 45.52, Groceries 5.88`), so nothing from the export is lost. Only a file mapped with the Buxfer template (the built-in one or a saved template for its header) reads tags this way; in any other file, a category such as `Project:2026` stays a plain category value. Rows without a category are categorized by rules. Rows imported into a bank-linked account dated on or before its opening balance extend its history without changing its balance (the opening balance shrinks and moves before them); later rows change the balance and, unless they duplicate a synced booking, show up as a difference to the reported bank balance.

## Buxfer

The built-in Buxfer template recognizes `ID,Date,Description,Currency,Amount,Type,Tags,Account,Status,Memo,IOU` and maps ID, ISO date, description, currency, signed dot-decimal amount (until Ufer tracks brokerage holdings, a settlement account stands for its cash plus securities at cost, so the template imports `Investment purchase` and `Investment sale` rows as hidden bookings with their exported amount and text: they are kept for reimport and later holdings, but count toward no balance, report or transfer pairing; `Capital gain` and `Capital loss` count as ordinary bookings), Type, Tags as category and Account as source account; Status, Memo and IOU are ignored. Any file can map a Type column by choosing that role; it is never suggested from a header name, because a bank export's "Transfer" can mean an external payment. Rows whose type is "Transfer" (or "Umbuchung"/"Übertrag") are saved as automatic transfers, which the transfer pairing links to their counterpart after confirmation; every other row is income or expense by its sign. Descriptions Buxfer shortened with "..." still match the full bank text during duplicate detection, because a shortened text is contained in the full one. The template declares these row conventions (amount-bearing tags split, hidden types, transfer types) on its definition; the mapping code applies whatever a template declares, other files use the default transfer types only, and a saved template for the Buxfer header takes the conventions from the built-in one.

## Templates

A file whose header row equals a template's, cell by cell after trimming, is mapped with that template automatically, and the page says so ("Detected as Buxfer export" or "Using your template …"); Map manually switches back to the detected number and date format and suggested roles while keeping the current encoding and delimiter, and a match that is not applied is offered with Apply template.

After a confirmed import the mapping can be saved as a named template, or, when a saved template matches the header (also after Map manually), that template is updated: column positions in the exact header row (so repeated header names keep their roles), the date and decimal format, and optionally the chosen existing accounts by source value and existing categories by category value. Saved templates are stored server-side in `import_templates` (changeset 0013) and are unique per header row and per name (ignoring case). The import page lists saved and built-in templates together, saved ones first, which is also the matching order, so a saved template for the Buxfer header wins. Built-in templates stay defined in code: they are listed as "Buxfer export (built-in)", cannot be renamed or deleted, and Duplicate saves an editable copy. Saved templates can be renamed and deleted. Remembered accounts or categories that no longer exist fall back to the defaults. Reimporting never updates rows that are already imported. There is no PDF importer or dedicated migration wizard for another product.

## Balance series

The fixed-schema balance series import (`date,balance,currency`) was retired ([#282](https://github.com/daberni/ufer/issues/282)): balances are derived from transactions, so a balance on a past date is recorded with Update balance on the account, and transaction history comes through the mapped import. Opening balances and adjustments booked by earlier balance imports stay unchanged.
